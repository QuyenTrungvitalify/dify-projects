## Context — why 033 stopped at ④, and why that's the same gap as "auto-mode collapsed the phases"

033 added Ask at Analyze/Spec/Implement by resuming `sessionIds[task.phase]` — the phase's own Claude session already holds the requirement + the artifact-in-progress, so an Ask there is cheap and well-informed. 033 explicitly declared ④ and terminal `done`/`cancelled` **out of scope**, for a structural reason, not a product one: **there is no session to resume.**

Confirmed directly:
- [task.ts:127](../../apps/builder/server/state/task.ts#L127) — `sessionIds: { analyze?: string; spec?: string; implement?: string }`. There is **no `test` key**, in any revision — ④ has never persisted a turn session, because ④ has never *run* a Claude turn for its own gate.
- [live-test.ts:145-146](../../apps/builder/server/lib/live-test.ts#L145-L146) — ④-live "always ends parked at a human gate (`test_result` or `infra_degraded`) or `error`; never silently `done`" — and the whole sub-orchestrator is backend code (import/publish/mint/run + [runJudge](../../apps/builder/server/lib/live-test.ts#L78)), not a resumable authoring turn.
- [orchestrator.ts:534-578](../../apps/builder/server/lib/orchestrator.ts#L534-L578) (`runTestAndFinish`, ④-static) — sets `task.phase = 'test'` ([:541](../../apps/builder/server/lib/orchestrator.ts#L541)), runs the (turn-less) linters via `runReport`, and parks at `awaiting_import` ([:563](../../apps/builder/server/lib/orchestrator.ts#L563)) or `still_failing` ([:572](../../apps/builder/server/lib/orchestrator.ts#L572)) gates, or goes **straight to `task.status = 'done'`** ([:577](../../apps/builder/server/lib/orchestrator.ts#L577)) for `none`/`cloud` deploys (or an accepted lint failure) — no turn, no session, sometimes no gate at all in between.
- [App.tsx:141-173](../../apps/builder/web/src/components/App.tsx#L141-L173) (`send()`) — at `status==='done'` or `'cancelled'` ([App.tsx:156](../../apps/builder/web/src/components/App.tsx#L156)), the composer's plain Send **always** calls `store.start()` ([App.tsx:157](../../apps/builder/web/src/components/App.tsx#L157)), a brand-new build (placeholder `phDescribeAnother`, [App.tsx:417](../../apps/builder/web/src/components/App.tsx#L417)); there is no "reply to this finished/abandoned build" path today. **This is exactly the call D3's resolution replaces for these two statuses** — see Design decisions below.

**The reduction that scopes this spec.** The task explicitly asks: what happens when `confirmMode==='auto'` collapses ①→②→③ into one hands-free run (`maybeAutoAdvance`, [orchestrator.ts:251](../../apps/builder/server/lib/orchestrator.ts#L251)) and the user wants to ask a question once it stops? Look at **where** `auto` is willing to hard-stop: every flag check in `maybeAutoAdvance` —
```
orchestrator.ts:254  still_failing   → auto HARD-STOPS (§D / AC #25)
orchestrator.ts:255  awaiting_import → deploy is ALWAYS a human decision (spec 014 D1)
orchestrator.ts:256  test_result     → live-test verdict → human decides (spec 032 B4)
orchestrator.ts:257  infra_degraded  → degrade-to-static → human decides (spec 032 D1c)
```
— every one of these is set with `task.phase === 'test'` (confirmed above: `still_failing`/`awaiting_import` at [orchestrator.ts:563,572](../../apps/builder/server/lib/orchestrator.ts#L563-L572), `test_result`/`infra_degraded` at [live-test.ts:167,174](../../apps/builder/server/lib/live-test.ts#L167-L174)). **There is no auto-mode hard-stop flag that isn't a ④ flag.** So "let the user ask a question once `auto` has run out of road" and "let the user ask a question at a ④ gate" are **the same underlying gap, not two**. Solving Ask-at-④ automatically satisfies the auto-mode framing; no auto-mode-aware branch, no extra mechanism, no new detection of "is this an auto-collapsed run" is needed anywhere in this spec.

One asymmetry worth naming precisely so the reduction isn't oversold: a `none`/`cloud` deploy (or an accepted-lint-failure) build can go straight from `running` to `done` ([orchestrator.ts:576-578](../../apps/builder/server/lib/orchestrator.ts#L576-L578)) **without ever parking at a ④ gate at all** — no flag, no pause, nothing to Ask at. `auto` never silently reaches that `done` without passing through one of the four flags above *when it would have stopped anyway* — but a `selfhost`-free build was never going to stop at ④ regardless of `confirmMode`. So "Ask at the live ④ gates" fully covers the auto-mode motivating case, but does **not**, by itself, cover "ask a question about a `none`/`cloud` build that finished quietly." That residual gap is exactly what D3 closes — the terminal-`done`/`cancelled` entry point below, not a new ④-adjacent flag.

**This spec's job:** make conversational Q&A available (a) at any of the four ④ gates (`test_result` / `infra_degraded` / `awaiting_import` / `still_failing`, all `task.phase==='test'`, `task.status==='awaiting_confirm'`) and (b) after a build reaches terminal `status==='done'` **or** `status==='cancelled'`, **without** a resumable phase session and **without** touching the gate FSM. The resolution (D3) applies **identically** to both terminal statuses — a `cancelled` build may simply have fewer artifacts available on disk depending on which phase it was cancelled at (e.g. cancelled mid-Implement has no `report.json` yet); D1's "seed with whatever exists, degrade gracefully" already handles that with **no new mechanism** for `cancelled` specifically.

## Design decisions

- **D1 · Fresh, non-resumed turn, seeded via the prompt (recommend locked).** Since no session exists to `--resume`, every ④/terminal (`done` or `cancelled`) Ask spawns a **new** `ClaudeSession`, same shape as `runJudge` ([live-test.ts:78-117](../../apps/builder/server/lib/live-test.ts#L78-L117)): no tools required, `DIFY_*` stripped, all context folded into the prompt rather than implied by turn history. The prompt is seeded with whatever of the following exist on disk/on the task: `task.requirement`, `SPEC.md` (`task.artifacts.spec`, the same path `implement.md` re-reads per [phases.ts:100](../../apps/builder/server/lib/phases.ts#L100)), `main.yml` (`task.artifacts.implement` / `workflowDir(t)/workflows/${t.workflowFile}`, [phases.ts:89](../../apps/builder/server/lib/phases.ts#L89)), `report.json` (`runArtifact(task,'report.json')`, [phases.ts:107](../../apps/builder/server/lib/phases.ts#L107)), and — when the build ran `test_live` — `task.liveTest` (the persisted `LiveTestResult` + judge verdict, set at [live-test.ts:165](../../apps/builder/server/lib/live-test.ts#L165), which `report.json` does NOT itself contain — the judge's per-criterion verdict only lives on the task object). Each read follows `readCriteria`'s try/catch-empty-on-missing pattern ([live-test.ts:26-33](../../apps/builder/server/lib/live-test.ts#L26-L33)) — an absent file degrades the seed, it never fails the Ask. This is the SAME degrade-gracefully path a `cancelled` build's partial artifacts hit — no `cancelled`-specific branch needed.
- **D2 · Follow-up questions in the same ④/`done`/`cancelled` conversation resume a NEW dedicated session slot, not `sessionIds['test']` (recommend locked).** `'test'` is deliberately absent from `sessionIds`'s type today for the FSM's own reasons (no turn ever runs "as" phase ④) — repurposing it would conflate "a ④/terminal Ask happened" with "a ④ phase turn happened," which is false and would confuse any future code that reads `sessionIds` to mean phase progress. Instead: add a new, precise, optional field to `Task` at [task.ts:127](../../apps/builder/server/state/task.ts#L127) — `sessionIds: { analyze?: string; spec?: string; implement?: string; askTest?: string }`. The FIRST ④/`done`/`cancelled` Ask's returned `session_id` is persisted into `sessionIds.askTest`; a subsequent Ask in the same visit `--resume`s it instead of spawning fresh again — mirrors 033's own D5 (shared session; "each turn restates its own instruction" reasoning applies identically here: a follow-up like "why did that criterion fail?" needs the prior Q&A in context to make sense). **`askTest` is purely a chat-continuity convenience** — it is never read by `computeGate`, `runPhaseAndGate`, `maybeAutoAdvance`, or any FSM code; it exists only so `askTestWithin` can decide fresh-spawn vs resume. *(Open Q1, mirroring 033's own OQ1: if a stale `askTest` session ever resumes across an intervening file change — e.g. the user Accepted `still_failing` and the report was regenerated between two Asks — should it detect staleness and re-seed fresh instead of resuming? Default: resume unconditionally, matching 033's own choice not to over-engineer staleness detection; revisit with real use.)*
- **D3 · Terminal entry point — Send at `done`/`cancelled` defaults to Ask; starting a new build moves to the sidebar "+" (CLOSED — was OPEN).** Mirrors 033's own D2 pattern exactly: default to Ask, an explicit SEPARATE action for anything else. The resolution:
  - At **both** `task.status==='done'` and `task.status==='cancelled'`, the composer's plain Send now calls `store.ask(text)` (033's action, reused verbatim — [033-builder-gate-qa-chat-mode.md:413](033-builder-gate-qa-chat-mode.md#L413)), hitting this spec's widened `/ask` route, **not** `store.start()`. `App.tsx`'s `send()` ([App.tsx:141-173](../../apps/builder/web/src/components/App.tsx#L141-L173)) gains a genuinely new branch — `status==='done'||status==='cancelled' → store.ask(text)` — replacing today's fall-through into `store.start(msg, atts)` for those two statuses specifically ([App.tsx:156-157](../../apps/builder/web/src/components/App.tsx#L156-L157)). `view==='empty'` keeps routing to `store.start()`, byte-unchanged.
  - **This explicitly SUPERSEDES 033 §3's own routing table's `done | cancelled | empty-view → store.start()` row** ([033-builder-gate-qa-chat-mode.md:407](033-builder-gate-qa-chat-mode.md#L407)). 033's table was correct as of 033's OWN scope — 033 D4 declared terminal states entirely out of scope for that spec ([033-builder-gate-qa-chat-mode.md:163-170](033-builder-gate-qa-chat-mode.md#L163-L170)) — **this spec is the one that changes that row, deliberately.** A reader comparing 033 and 034 side-by-side should read 033's row as "true when 033 shipped, superseded by 034 §1/D3 for `done`/`cancelled` specifically" — 033's `error` row is untouched, only `done`/`cancelled` move.
  - Starting a genuinely NEW build no longer happens via the terminal composer AT ALL — it happens via the EXISTING sidebar "+" entry point: the plain "New task" button ([Sidebar.tsx:175](../../apps/builder/web/src/components/Sidebar.tsx#L175)), the per-project "+" ([Sidebar.tsx:86](../../apps/builder/web/src/components/Sidebar.tsx#L86)), or the per-workflow "+" ([Sidebar.tsx:55](../../apps/builder/web/src/components/Sidebar.tsx#L55), spec 030) — all three already call `onNewTask`/`newTask(opts?)` ([App.tsx:211](../../apps/builder/web/src/components/App.tsx#L211)), which calls `store.resetToNew()` ([store.ts:632-650](../../apps/builder/web/src/store.ts#L632-L650)), setting `task.value = null` ([store.ts:635](../../apps/builder/web/src/store.ts#L635)) and flipping the view back to `EmptyState` ([App.tsx:321-329](../../apps/builder/web/src/components/App.tsx#L321-L329)). Completely unchanged by this spec.
  - **Consequence for the terminal composer's SETTINGS ROW.** Today it renders unlocked (workflow/deploy/confirm/fast/test, via `settingsSubset`/`onSettings`, [App.tsx:416](../../apps/builder/web/src/components/App.tsx#L416)) because Send there currently means "configure + start a new build." Once Send there means Ask instead, that settings row has no effect when pressed — a stale "configure your next build" affordance Send no longer acts on, which would mislead a user into thinking a toggled setting does something. **Fix: remove the settings row entirely** from this Composer instance ([App.tsx:414-420](../../apps/builder/web/src/components/App.tsx#L414-L420)) — no `settings`/`onSettings`/`workflows` props, a new Ask-specific placeholder in place of `phDescribeAnother` ([App.tsx:417](../../apps/builder/web/src/components/App.tsx#L417)). "Configure a new build" now lives ONLY at the empty-view composer ([App.tsx:321-329](../../apps/builder/web/src/components/App.tsx#L321-L329), unchanged) — the terminal composer becomes JUST a question-input box.
  - At `cancelled` specifically: the EXISTING Restore action ([Chat.tsx:345-350](../../apps/builder/web/src/components/Chat.tsx#L345-L350) — reopens THIS build at its previous gate, wholly unrelated to Ask) stays available ALONGSIDE Ask — two independent, coexisting actions. Nothing about Restore changes.
  - At `done`: there is no Restore — [tasks.ts:400-402](../../apps/builder/server/routes/tasks.ts#L400-L402) only accepts `task.status==='cancelled'` (400/409 otherwise), unaffected by this spec — only Ask is available here (plus, per the sibling spec 035, a distinct "edit this workflow" action that spec adds; referenced by name only).
  - **Why this is safe, unlike the "double-meaning" risk the original draft worried about for a mode-toggle-on-the-same-composer option:** that risk existed only because the terminal composer's OTHER fields (workflow/deploy/confirm-mode) meant "settings for the next build" at the same time a mode chip would mean "ask about THIS build" — a real double-meaning. Starting a new build ALREADY has its own dedicated, separate entry point today (the sidebar "+", spec 030) — so once that's the sole place "start new" lives, the terminal composer never needs to carry the "next build" meaning at all. There's nothing left to overload: the risk is dissolved, not mitigated.
- **D4 · Reuse 033's `BUILDER_ASK_MODE` answer-only enforcement; the byte-snapshot/restore backstop is likely unnecessary here (recommend locked, with justification).** This turn is a normal `claude` child, so it inherits `DIFY_*`-stripped env + the PreToolUse permission-gate hook (spec 015, unconditionally). Layering 033's `BUILDER_ASK_MODE` env branch on top (the hook denies file-mutating tool calls while it's set) is a direct, verbatim reuse and this Ask is if anything an EASIER case than 033's: 033's phase-Ask runs alongside a session that has just been (or is about to be) actively editing `SPEC.md`/`main.yml` as ITS canonical artifact, so a slip needs a hard technical backstop. Here, `report.json` is produced entirely by non-LLM code — `report.ts`'s own module doc says plainly "Phase ④ Test&Report BACKEND (**no claude turn**)... re-runs the 3 linters and synthesizes `report.json`" ([report.ts:1-13](../../apps/builder/server/lib/report.ts#L1-L13)) — there is no sense in which a ④/`done`/`cancelled` Ask turn is "the gate's own artifact, mid-edit" the way 033's is; a stray write here would be a write to a file the turn has no legitimate reason to even open, not an over-eager edit of the thing it's supposed to be revising. Given that, 033's layer-2 (git-porcelain byte-snapshot-and-restore) backstop is **optional and likely unnecessary** — say so explicitly rather than mechanically carrying it over: the hook alone (layer 1) already denies the write pre-execution, and there is no "protect the in-progress artifact from an over-eager same-turn edit" scenario to backstop against. Stated honestly, though: the seed still *includes* `main.yml`/`SPEC.md` (D1) — the same artifacts 033 double-guards — so dropping layer 2 makes the permission-gate hook the **sole** guard for those files during a ④/terminal Ask. That is a deliberate single-point-of-failure ("layer 1 is the only guard now"), not "there is nothing to protect" — the difference from 033 is only that no *in-progress edit* raises the odds of a slip, not that the file is any less corruptible. If a future incident shows the hook alone insufficient, add the snapshot/restore then; don't pay for it speculatively.
- **D5 · Mandatory fix: Send at ④ currently hard-routes to `/reply` — without removing that carve-out, Goal #1/AC#1 ("Ask works at ④") are unreachable through the UI (locked, closes a load-bearing gap an adversarial review found).** 033's §3 routing table ([033-builder-gate-qa-chat-mode.md:386-390](033-builder-gate-qa-chat-mode.md#L386-L390)) pins `awaiting_confirm, phase==='test' → store.reply()` UNCONDITIONALLY — correct when 033 was written, since D4 (033's own) declared Ask categorically absent at ④ at that time. The concrete carve-out lives in `send()`'s `st === 'error' || ph === 'test'` disjunct ([App.tsx:163](../../apps/builder/web/src/components/App.tsx#L163)); the ④ gate's Composer instance is `App.tsx`'s NON-terminal (live) branch ([App.tsx:381-413](../../apps/builder/web/src/components/App.tsx#L381-L413)) — a genuinely DIFFERENT code path from the `done`/`cancelled` branch D3 above edits ([App.tsx:414-420](../../apps/builder/web/src/components/App.tsx#L414-L420)). Nothing in this spec's D3/§1/§2 touches the live branch or 033's `phase==='test'` row — so, as originally drafted, a plain Send at any ④ gate still calls `store.reply()` (re-running `runTestAndFinish`/`runLiveTest`, [orchestrator.ts:190-199](../../apps/builder/server/lib/orchestrator.ts#L190-L199)), never reaching `askTestWithin`. **Fix**: this spec supersedes 033's `phase==='test'` row too (alongside D3's `done`/`cancelled` row) by removing the `|| ph === 'test'` disjunct from `send()`, extending the SAME ask|change mode-chip mechanism (033 §3) to ④:
  ```
  awaiting_confirm, phase==='test', mode==='ask' (default)   → store.ask(text)        // this spec's askTestWithin
  awaiting_confirm, phase==='test', mode==='change'          → store.reply(text,label) // whichever reply-kind
                                                                                        // action THAT ④ gate
                                                                                        // already defines, unchanged
                                                                                        // (test_result has one
                                                                                        // today — orchestrator.ts's
                                                                                        // own comment: "(changes
                                                                                        // is a /reply)")
  ```
  **The mode-chip machinery is NOT free at ④ — this is real FE work, not the no-op an earlier draft assumed.** The mode chip ([App.tsx:386](../../apps/builder/web/src/components/App.tsx#L386)), the attach-hiding guard ([App.tsx:410](../../apps/builder/web/src/components/App.tsx#L410)), and the Ask-aware placeholder ([App.tsx:245-247](../../apps/builder/web/src/components/App.tsx#L245-L247)) all render under `dockedGate` ([App.tsx:241-242](../../apps/builder/web/src/components/App.tsx#L241-L242)), which is hard-defined as `awaiting_confirm && phase∈{analyze,spec,implement}` — it **EXCLUDES `test`**. So removing the `send()` carve-out alone makes the *default* work (plain Send at ④ → `store.ask()`), but leaves two holes: (a) no visible ask/change indicator at ④, so arming change-mode via the gate button (`onArmChange`, [App.tsx:349](../../apps/builder/web/src/components/App.tsx#L349)) is invisible to the user; (b) the attach affordance stays enabled in ask-mode at ④ (`dockedGate && mode==='ask'` is `false` there), so a file attached to an Ask is silently dropped — the exact 033 F5 bug that guard exists to prevent. **You cannot fix this by widening `dockedGate`**, because the SAME predicate also drives the docked action BAR ([App.tsx:364](../../apps/builder/web/src/components/App.tsx#L364)), which §2 deliberately does NOT want at ④ (④ gate actions render inline, [App.tsx:239-240](../../apps/builder/web/src/components/App.tsx#L239-L240)). **Fix: introduce a separate `askableGate` predicate** (`awaiting_confirm && phase∈{analyze,spec,implement,test}`) gating the chip + attach-guard + placeholder, and leave `dockedGate` (bar-only) unchanged so ④'s actions stay inline. Scoped into S3.
  **What this does NOT break — verified against the code:** Request-changes at ④ stays reachable after the carve-out is removed. The `test_result` gate defines `REPLY('changes','Request changes')` ([gate.ts:143](../../apps/builder/server/lib/gate.ts#L143)), and a `kind==='reply'` action renders a button wired to `onArmChange` ([Chat.tsx:247-248](../../apps/builder/web/src/components/Chat.tsx#L247-L248)) → `setMode('change')` → the `mode==='change'` row above sends `store.reply`. The other three ④ gates (`infra_degraded`/`awaiting_import`/`still_failing`) define no reply-kind action ([gate.ts:151-163](../../apps/builder/server/lib/gate.ts#L151-L163)), so Send there is unconditionally Ask — consistent with intent, nothing to disambiguate. This is the SAME class of gap D3 closes for the terminal branch, just for the OTHER Composer instance (the live/non-terminal one) — both are "this spec built a backend capability with no FE path reaching it," now both closed.

## Design

### §1 · Backend — fresh-seeded turn + session slot + route

**Route.** Generalize 033's `POST /api/tasks/:id/ask` rather than add a second endpoint: the wire contract (`{text}` in, `ask:answer` SSE out) is identical, only the VALIDATION differs. `/reply`'s own check ([routes/tasks.ts:314](../../apps/builder/server/routes/tasks.ts#L314)) accepts BOTH `task.status==='awaiting_confirm'` and `'error'` (the Retry-out-of-error path) — but 033's `/ask` deliberately narrows that: it 409s unless `task.status==='awaiting_confirm'` AND `task.phase∈{analyze,spec,implement}` (033 §1 — Ask has no meaning at `error`, there is no live parked gate to chat against). This spec widens 033's phase check to ALSO accept `awaiting_confirm` when `task.phase==='test'` (any of the four flags), **and** — per D3's resolution — `task.status==='done'` **or** `task.status==='cancelled'`; the `error`-exclusion stays untouched (033's own carve-out — no live parked gate to Ask against at `error`, unaffected by this spec). One endpoint, one client call site, branching happens server-side on `task.phase`/`task.status`:
- `analyze`/`spec`/`implement` + `awaiting_confirm` → 033's existing `askWithin` (resume `sessionIds[phase]`).
- `test` phase (any flag) + `awaiting_confirm`, OR `status==='done'`/`'cancelled'` (D3, resolved) → this spec's `askTestWithin` (below).

**`askTestWithin(task, text, ctx)`** — colocated with 033's `askWithin` (same module, [`server/lib/ask.ts`](../../apps/builder/server/lib/ask.ts), same turn-lock/dispatch/SSE plumbing), but its seed-gathering is `live-test.ts`'s `readCriteria`-style disk reads, not a `--resume`:
1. Acquire the turn lock exactly like any turn (a concurrent `/ask`/`/confirm`/`/reply` 409s, same as `/reply` today).
2. Gather the seed: `task.requirement`; `SPEC.md` at `task.artifacts.spec`; `main.yml` at `task.artifacts.implement`; `report.json` at the same repo-relative path `runArtifact(task,'report.json')` computes ([phases.ts:26,107](../../apps/builder/server/lib/phases.ts#L26)) — `runArtifact` itself is a module-private `const` in `phases.ts`, not exported, so `askTestWithin` DUPLICATES the path template rather than importing it, mirroring the one existing cross-module precedent for this exact need (`criteria.ts:51`'s own comment: "mirrors phases.ts `runArtifact`"); `task.liveTest` (stringified) when present. Each is independently optional (D1) — a `cancelled` build simply has fewer of these on disk, same handling, no branch.
3. Decide fresh-vs-resume: if `task.sessionIds.askTest` exists, `--resume` it (D2); else spawn a brand-new `ClaudeSession`, `runJudge`-shape ([live-test.ts:100-108](../../apps/builder/server/lib/live-test.ts#L100-L108)) — no tools, `BUILDER_ASK_MODE` set (D4).
4. Prompt: the seed block + the user's question + the same "answer conversationally; do NOT create/modify/delete any file" wrapper 033 uses.
5. Stream fragments as `ask:answer` (verbatim reuse of 033's SSE event — see §2), persist the new/continued `session_id` into `sessionIds.askTest` (D2).
6. Do **not** touch `task.gate`/`task.status`/`task.phase` — the ④ gate stays parked exactly as it was, and a `done`/`cancelled` task stays exactly as it was: `status` byte-unchanged, and (at `cancelled`) Restore's own eligibility check ([tasks.ts:400-402](../../apps/builder/server/routes/tasks.ts#L400-L402)) is completely unaffected — Ask never flips `cancelled` back to anything.
7. `/cancel` during a ④/`done`/`cancelled` Ask kills the child the same way 033's does (`setSession`/`clearSession`, [live-test.ts:106,114](../../apps/builder/server/lib/live-test.ts#L106-L114)).

Nothing here writes to `computeGate`, `runPhaseAndGate`, or `maybeAutoAdvance` — the FSM is byte-unchanged, same non-goal as 033.

### §2 · Frontend — SSE reuse, the terminal composer's reduction, and what this `qa` item needs that 033's didn't

**SSE**: reuse `ask:answer` + its terminal marker **verbatim** — the payload shape (streamed text, then done) is identical whether the turn resumed a phase session or was freshly seeded. The FE still appends a `{kind:'qa', question, answer}` thread item. (One consequence of D4 dropping layer-2: `askTestWithin` has no anomaly branch, so its `ask:done` is always `{ok:true}` — the `{ok:false, anomaly:{diff}}` path 033 defines simply never fires on this route; the `seededFrom` field below is the only addition to that marker.)

**One addition this shape needs that 033's phase-Ask didn't**: 033's Ask has full *implicit* context (it resumed the phase's own session, which already "knows" the requirement and the artifact-in-progress), so the thread item needs no extra provenance — the user trusts it's answering from the same conversation they've been having. A ④/`done`/`cancelled` Ask has no such implicit context — it was freshly assembled from whatever files happened to exist, per D1, and could silently be missing a piece (e.g. `report.json` not yet written on `infra_degraded`, or `SPEC.md` never produced by a `fastMode` merged-draft build, or a `cancelled` build missing whatever wasn't reached before it was cancelled). So extend the `qa` thread item (and the terminal `ask:done` marker — **not** the per-fragment `ask:answer` event, which is high-volume and replay-excluded per 033; `seededFrom` is one-shot metadata, so it rides the single `done` marker, ④/terminal case only) with an optional `seededFrom: string[]` — the list of sources actually folded in (e.g. `['requirement','SPEC.md','main.yml','report.json']`), rendered as a small caption under the answer bubble ("based on: requirement, SPEC.md, main.yml, report.json"). Phase Asks omit this field entirely (no behavior change to 033's rendering). This lets the user tell, at a glance, when an answer might be missing context rather than silently trusting a possibly-incomplete fresh-seed.

**Entry point (D3, resolved) — the SAME terminal composer, reduced, not a new surface.** At `task.status==='done'` or `'cancelled'`, the composer already rendered in that slot — App.tsx's free-settings branch, [App.tsx:414-420](../../apps/builder/web/src/components/App.tsx#L414-L420) — stops meaning "describe another build" and becomes Ask-only:
- `onSend` now calls `store.ask(text)` (033's action — [033-builder-gate-qa-chat-mode.md:413](033-builder-gate-qa-chat-mode.md#L413)), not `store.start()`; `send()`'s new `done|cancelled → store.ask` branch is described in D3 above.
- The `settings={settingsSubset}` / `onSettings={onSettings}` / `workflows={workflows}` props ([App.tsx:416](../../apps/builder/web/src/components/App.tsx#L416)) are DROPPED from this Composer instance entirely — no workflow/deploy/confirm/fast/test row renders here anymore (D3's "consequence for the settings row"). The placeholder changes from `phDescribeAnother` ([App.tsx:417](../../apps/builder/web/src/components/App.tsx#L417)) to the new Ask-specific string `phAskAboutBuild` ("Ask about this build…").
- No pinned/docked action bar is needed here — 033 D7's docked bar is scoped to `awaiting_confirm && phase∈{analyze,spec,implement}` ([033-builder-gate-qa-chat-mode.md:433-434](033-builder-gate-qa-chat-mode.md#L433-L434)), unaffected; a terminal task has no live gate to pin a bar to. The thread simply grows with `{kind:'qa'}` items, same shape as a ④ Ask — no mode chip is needed either, since there is no "Request changes" alternative at a terminal status (nothing to resume, nothing to re-run): Send is unconditionally Ask, with no ambiguity to disambiguate.
- At `cancelled` specifically, the last gate card's inline Restore button ([Chat.tsx:345-350](../../apps/builder/web/src/components/Chat.tsx#L345-L350), untouched) still renders above the composer — Ask and Restore are two independent, coexisting actions; pressing one has no effect on the other's availability. At `done` there is no Restore ([tasks.ts:400-402](../../apps/builder/server/routes/tasks.ts#L400-L402)), only Ask (plus, per sibling spec 035, a separate "edit this workflow" action — referenced by name only).
- Starting a genuinely new build has no entry point on this composer at all anymore — see D3's sidebar-"+" resolution; `EmptyState` ([App.tsx:321-329](../../apps/builder/web/src/components/App.tsx#L321-L329)) remains the ONE place with a settings row for a next build, unchanged.

### §3 · Security (spec 015 + 033 §4 — invariant, unchanged)
Same as 033 §4: `DIFY_*` stripped, permission-gate hook active, `BUILDER_ASK_MODE` denies mutating tool calls (D4). The injected prompt content (requirement/SPEC.md/main.yml/report.json) is the build's OWN artifacts, already trusted at this point in the pipeline (SPEC.md/main.yml passed Implement's confinement check to exist at all; report.json is backend-synthesized, never turn-authored) — no new untrusted-input surface versus what earlier phases already handled. This holds identically whether the build ended at `done` or `cancelled` — a `cancelled` build's partial artifacts are no less trusted than a `done` build's complete ones, they're just fewer of them (D1).

## Goals
1. Extend 033's north star (chat, no phase re-run, answer-only) to the ④ Test gates (`test_result`/`infra_degraded`/`awaiting_import`/`still_failing`) — a question there gets a message↔message answer, the ④ gate stays parked exactly as it was. Achievable ONLY once D5's fix lands (033's own `phase==='test'` routing carve-out removed) — an earlier draft of this spec built the backend half of this goal without the FE route reaching it; D5 closes that.
2. By the Context reduction, this also satisfies "let me ask once `auto` stops" — no separate auto-mode mechanism is built or needed.
3. Extend the same mechanism to a terminal task — `status==='done'` **or** `status==='cancelled'` — so a finished or abandoned build remains askable. Per D3's resolution, this replaces the composer's *previous* "Send here starts a new build" meaning at those two statuses specifically; starting new now lives exclusively at the sidebar "+" (unchanged).
4. Every such Ask is a **fresh-seeded**, not resumed, turn (D1), using whatever of requirement/SPEC.md/main.yml/report.json/liveTest exist — this degrades gracefully for a `cancelled` build's partial artifact set with no new mechanism.

- No extension to the `error` status — 033's own carve-out stands, untouched: `error` stays on `/reply`-Retry ([tasks.ts:314](../../apps/builder/server/routes/tasks.ts#L314)), there is no live parked gate to Ask against there. (033's own routing table never paired `error` with `cancelled` — it groups `done`/`cancelled`/empty-view together under `store.start()` and keeps `error` as its own, separate row, [033-builder-gate-qa-chat-mode.md:407-408](033-builder-gate-qa-chat-mode.md#L407-L408); this spec moves `cancelled` OUT of that `store.start()` grouping per D3, while `error` stays exactly where 033 left it.)
- No auto-classification of Ask vs a new build/change — Ask here stays an explicit mode (033 D1), never inferred from text.

- No change to the sidebar "+" / `newTask()`/`onNewTask` new-build entry point ([App.tsx:211](../../apps/builder/web/src/components/App.tsx#L211), [Sidebar.tsx:55,86,175](../../apps/builder/web/src/components/Sidebar.tsx#L55)) — D3 ROUTES "start new" to it, it does not modify it.

## Acceptance criteria
1. At any of the four ④ gates (`test_result`/`infra_degraded`/`awaiting_import`/`still_failing`), a plain composer Send (default `mode==='ask'`, per D5's routing fix) reaches `askTestWithin` via `/ask` and streams a message↔message answer via `ask:answer`, and the gate's `status`/`gate.flag`/`phase` are byte-unchanged before/after (still `awaiting_confirm`, same actions, same flag). Explicitly NOT `store.reply()` unless `mode==='change'` — the whole point of D5.
2. An Ask turn — at ④, or after `done`/`cancelled` — never touches `main.yml`/`SPEC.md`/`report.json` on disk (byte-identical before/after) — `BUILDER_ASK_MODE` + the permission-gate hook hold (D4), regardless of which case it is.
3. A second Ask in the same ④/`done`/`cancelled` conversation resumes `sessionIds.askTest` (D2) and its answer can reference the first Q&A; `sessionIds.analyze`/`spec`/`implement` are never read or written by this path.
4. `/cancel` during a ④/`done`/`cancelled` Ask stops it cleanly with no clobber of the parked gate (or of `done`/`cancelled`'s own status).
5. The FSM, `/confirm`, `/reply`, golden-build, and advance-loop tests stay green — no `computeGate`/`maybeAutoAdvance` change (mirrors 033 AC #3).
6. At `status==='done'` or `'cancelled'`, the composer's plain Send routes to `askTestWithin` via the SAME `/ask` route — not `store.start()`; the free-settings Composer instance ([App.tsx:414-420](../../apps/builder/web/src/components/App.tsx#L414-L420)) drops `settingsSubset`/`onSettings`/`workflows` entirely and shows an Ask-specific placeholder; starting a genuinely new build is reachable ONLY through the sidebar "+" (`newTask()`, [App.tsx:211](../../apps/builder/web/src/components/App.tsx#L211) / [Sidebar.tsx:55,86,175](../../apps/builder/web/src/components/Sidebar.tsx#L55)), unchanged.

## Biggest risks (+ mitigations)
0. **(Found by adversarial review, now closed by D5) An earlier draft of this spec built `askTestWithin`/the
   widened `/ask` route without ever wiring the ④ gate's OWN composer branch to call it** — 033's own
   `phase==='test' → store.reply()` routing row was left untouched, so a plain Send at ④ would have kept
   calling `/reply` regardless of this spec shipping, making Goal #1/AC#1 unreachable through the UI. D5 fixes
   this by extending the mode-chip routing predicate to ④. Listed here, not just in D5, because it's exactly
   the class of risk this section exists to name: a backend capability with no FE path reaching it.
1. **033's own doc contains TWO routing-table rows this spec supersedes** (`done|cancelled → store.start()`,
   [033-builder-gate-qa-chat-mode.md:407](033-builder-gate-qa-chat-mode.md#L407); and
   `phase==='test' → store.reply()`, [033-builder-gate-qa-chat-mode.md:386-390](033-builder-gate-qa-chat-mode.md#L386-L390),
   D5). Mitigated already, not just planned: 033's own file carries an explicit "superseded by 034" note at
   both rows as of this revision, so a reader of 033 in isolation isn't misled.
2. **Removing the terminal composer's settings row is a user-visible behavior change** — anyone who used a finished/cancelled build's composer to pre-configure workflow/deploy/confirm for their next build loses that specific affordance at that specific call site. Mitigation: deliberate, and low-cost — the sidebar "+" (spec 030, already shipped) is the exact equivalent, pre-existing surface; nothing new to learn, just a relocated (and now singular) place to configure a next build.
3. **A fresh-seeded turn answers LESS accurately than 033's resume-based Ask** (no implicit conversation history, only whatever got assembled into the prompt) — and a `cancelled` build's thinner artifact set makes this more likely there than at `done`. Mitigation: D1's "seed with everything available" (requirement + SPEC.md + main.yml + report.json + liveTest, whichever exist) + §2's `seededFrom` caption so an incomplete seed is visible rather than silently trusted.
4. **`sessionIds.askTest` resumes across a state change it doesn't know about** (e.g. the report was regenerated between two Asks, or a `cancelled` build's on-disk artifacts differ from what `askTest` was originally seeded with, per D2's Open Q1) — a follow-up answer could reference stale numbers. Mitigation: none in v1 (matches 033's own choice not to detect staleness); revisit if real use shows it's confusing.

## Open questions
- **D3 · RESOLVED — see Design decisions above.** The original draft weighed three options: (a) a separate small "Ask about this build" control; (b) a mode toggle on the SAME terminal composer; (c) no terminal Q&A in v1. The resolution is (b)-shaped (Send on the same composer routes to Ask) but WITHOUT the double-meaning risk the original draft flagged for (b) — that risk existed only because the terminal composer's other fields (workflow/deploy/confirm-mode) meant "settings for the next build" at the same time a mode chip would mean "ask about THIS build." Starting a new build ALREADY has its own dedicated, separate entry point today — the sidebar "+" (`newTask()`/`onNewTask`, spec 030, [Sidebar.tsx:55,86,175](../../apps/builder/web/src/components/Sidebar.tsx#L55)) — so once that's understood as the sole place "start new" lives, the terminal composer never needs to carry the "next build" meaning at all: there's nothing left to overload, so the risk is dissolved rather than merely mitigated.
- **OQ1 (D2)** — see D2's inline Open Q1: resume `askTest` unconditionally, or detect staleness (file changed since the session was seeded) and re-seed fresh? Default: resume unconditionally; revisit with real use.
- **OQ2** — should `seededFrom` (§2) also surface *which specific fields were empty/missing* (e.g. "SPEC.md: not found") rather than just which were included, so a thin answer is explainable rather than just flagged? Default: list only what WAS included (simpler); revisit if users ask "why didn't it know X."
