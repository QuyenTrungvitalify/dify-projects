# Spec 027 — Analyze `find_query`: truthful provenance, lean from-scratch artifact

**Status**: Draft
**Effort**: XS (umbrella — all items doc/skill-level; **zero backend logic change**; the only runtime delta is one cosmetic Analyze-gate line — see No-disruption #2)
**Depends on**: [019](019-builder-output-quality-and-lean-roadmap.md) (O2 introduced `pattern`/`features`/`find_query` into `analyze.json` and the coverage advisory). **Relates to** [026](026-authoring-gate-completeness-and-truth.md) (same "smaller / stricter / more honest, never larger" bar; the unbuilt pattern-delta diff is 026-class deferred work).

> **Thesis.** O2 (spec 019) added `find_query` to `analyze.json` so a previously *invisible* pattern-pick decision becomes **auditable** — "show your work". Two cheap defects now make that field lie instead of inform: (1) [analyze.md](../../.claude/skills/dify-build/analyze.md) — the *only* phase that records `find_query` — documents it in a **non-runnable shorthand** (`find.py --has …`) that contradicts the canonical form its **own sibling phases already use**, hides the real `tools/dify_base/` path, and would be **denied by the turn's permission hook** if executed; and (2) the **from-scratch branch** (no seed) invites the turn to *fabricate* `find_query`/`pattern`/`change_points` for a workflow that does not exist yet — pure guesswork recorded as provenance. This spec makes `find_query` **either a true record or absent** — never a plausible fabrication. It is **doc/skill-only**: the backend already treats every field as optional, so no backend logic or advisory output changes — the only runtime delta is a cosmetic Analyze-gate line (No-disruption #2). The one *additive* path (make the field actually drive automation / build the pattern-delta diff) is **explicitly deferred** with its trigger stated, so the umbrella cannot bloat.
>
> **The bar (carried from 026):** *tối ưu, hiệu quả nhất, nhưng không phình to.* Every item makes the skill **more honest or smaller** — none adds a subsystem.

## Context — what O2 built, and the two seams it left

O2 ([019 §128](019-builder-output-quality-and-lean-roadmap.md)) had the Analyze phase persist the chosen `pattern` + the needed `features` + the `find.py` query that justified them, then surface a **coverage advisory** when `features(pattern) ⊉ features(analyze.json)`. The motivation was explicit ([019:32-33](019-builder-output-quality-and-lean-roadmap.md)): *"nothing constraining or persisting the choice; **a wrong pick is invisible** until runtime."*

A two-run A/B of the **from-scratch** path (requirement: *"LLMを使用してシンプルなワークフローを作成します"*) exposed the seams:

- **Run A** (`.runs/1782214265113`) recorded `"find_query": "find.py --has llm"`.
- **Run B** (`.runs/1782214953934`) recorded `"find_query": ".venv/bin/python tools/dify_base/find.py --has llm"`.

Same input, **materially different artifacts** — and Run A's value is **not runnable**:

1. **The documented command form is wrong — and only in `analyze.md`.** **Verified:** `find.py` does not exist at `tools/` (it lives at [`tools/dify_base/find.py`](../../tools/dify_base/find.py)); `.venv/bin/python tools/dify_base/find.py --has llm` returns 33 matches. The skill's *other* phase files already say so —
   - [spec.md:19-20](../../.claude/skills/dify-build/spec.md): `.venv/bin/python tools/dify_base/find.py --json --has <feature>` ✅
   - [implement.md:24](../../.claude/skills/dify-build/implement.md): `.venv/bin/python tools/dify_base/find.py --json --has <feature>` ✅
   - but [analyze.md:28](../../.claude/skills/dify-build/analyze.md) (run instruction) and [:48](../../.claude/skills/dify-build/analyze.md) (the `find_query` example) say `find.py --has <feature>` / `e.g. find.py --has iteration --has file-input` ❌ — the shorthand a turn faithfully copies **into `find_query`**. (The same `find.py` token also appears at [:29-30](../../.claude/skills/dify-build/analyze.md) and [:47](../../.claude/skills/dify-build/analyze.md) as *feature-vocabulary*, not a runnable command — those legitimately stay; A1 fixes only the two command sites.) `analyze.md` is the **sole outlier**, and it is the one file that records the field.
2. **The shorthand is also hook-denied.** The build turn's permission hook is allowlist-first: [permission-gate.ts:54-60](../../apps/builder/server/hooks/permission-gate.ts) admits **only** `.venv/bin/python tools/dify_base/find.py …`. Run A's `find.py --has llm` hits the default-deny tail (*"command not in the Builder allow-set: find.py"*); even `.venv/bin/python tools/find.py …` is denied (*"script not in the allow-set"*) **and** the file is absent. So a turn that *copies the doc* can only ever **record a string it could not have run** — exactly Run A.
3. **From-scratch fabrication + non-determinism.** The empty-seed branch ([analyze.md:15-16](../../.claude/skills/dify-build/analyze.md)) says *"write `seed:null` and a one-line note … then STOP"* — but the full artifact schema ([:44-54](../../.claude/skills/dify-build/analyze.md)) tempts the turn to fill `pattern`/`features`/`find_query`/`change_points` anyway. With **no seed to classify**, those are forward-looking guesswork: Run A picked `pattern:"custom"`, Run B picked `pattern:"multi-step-llm"` — and `find_query` describes a classification that **never happened**.

### Why this is worth fixing but stays XS

`find_query` is currently **write-only in production**. **Verified by full consumer trace:** [analysis.ts:96-97](../../apps/builder/server/lib/analysis.ts) parses it into `task.analysisFindQuery`, but **no production code reads** `analysisFindQuery` — it is only *declared* in the task/web types ([task.ts:96](../../apps/builder/server/state/task.ts), [types.ts:72](../../apps/builder/web/src/types.ts)) and *asserted* in a parse round-trip test ([analysis.test.ts:57](../../apps/builder/test/analysis.test.ts)); nothing renders it or acts on it. The advisory ([analysis.ts:65-73](../../apps/builder/server/lib/analysis.ts)) consumes only `pattern`+`features` and computes coverage by reading `tools/dify_base/index.json` **directly** (it never executes the recorded command), and the UI renders only `analysisPattern`+`patternAdvisory` ([Chat.tsx:163-164](../../apps/builder/web/src/components/Chat.tsx)). The bigger use O2 cited — a *pattern-delta diff* — is **unbuilt by design**: [diff.ts:80-81](../../apps/builder/server/lib/diff.ts) records it as *"a true pattern-delta is a **Phase-3+ enhancement**."* So the field's only present consumer is a **human reading `analyze.json`** — which is precisely the consumer a wrong command form fails. Fixing the doc + scoping the field is therefore the entire job; **no code need change**.

## Goals

1. **A recorded `find_query` is always runnable** — it matches the canonical form the rest of the skill already uses, so a human (or a future automated consumer) can copy-paste and reproduce.
2. **No fabricated provenance** — when no `find.py` query was actually run (the from-scratch path), `find_query` is **absent**, not invented; `pattern` defaults to the honest `custom`.
3. **The field's status is documented, not surprising** — a future reader sees that `analysisFindQuery` is intentionally persisted-but-unread-by-production (human-audit + the deferred pattern-delta diff; only the task type declares it and a parse test references it), so it is neither "fixed" as a bug nor silently deleted.
4. **Strictly doc/skill-level** — no backend behavior change, no schema change, no new gate, no advisory rewrite. Additive forks deferred, not dropped.

## Non-goals (the leanness boundary)

- **Do NOT make the advisory execute `find_query`.** It correctly derives coverage from `index.json`; running a recorded command would re-introduce nondeterminism and fight the permission-hook sandbox that exists to constrain command execution. The recorded command is **provenance, not an instruction**.
- **Do NOT build the pattern-delta diff** ([diff.ts:80-81](../../apps/builder/server/lib/diff.ts) Phase-3+ / 026-class). This spec only makes the data that feature would inherit **truthful**, keeping the option cheap — it does not open it.
- **Do NOT drop `find_query` from the schema** (the considered alternative — see fork F-A). Spec 019 deliberately persisted it as the anchor for the future diff; removing it now trades a one-line doc note for churn-on-re-add.
- **No re-spec of 019/O2's advisory semantics**; `pattern`+`features` stay the advisory's only inputs.

## No-disruption discipline

1. **Back-compat is automatic.** Every field is already optional at the parse layer ([analysis.ts:88-98](../../apps/builder/server/lib/analysis.ts) — `applyAnalysisToTask` no-ops on absent fields). An older `analyze.json` (with the shorthand, or with a from-scratch `find_query`) still parses; the advisory still computes from whatever `pattern`/`features` are present. So A1/A2 cannot break an in-flight or replayed task.
2. **Honest from-scratch pattern keeps the advisory silent — correctly.** With `pattern:"custom"`, [`patternFeatures` returns `null`](../../apps/builder/server/lib/analysis.ts) → no advisory. That is the *intended* N/A for a build with no seed to match, and it is what A2 standardizes (vs Run B's `multi-step-llm`, which is an indexed pattern that merely happens to cover `llm`, so its advisory is *also* empty — but for the wrong reason: it over-claims a classification that never ran). **One cosmetic delta (not "no change"):** because A2 now always sets `pattern:"custom"` on from-scratch, `task.analysisPattern` is populated, so the Analyze gate renders a deterministic `pattern: custom` line ([Chat.tsx:164](../../apps/builder/web/src/components/Chat.tsx)) where today's `seed:null`-only artifact (per [analyze.md:15-16](../../.claude/skills/dify-build/analyze.md)) leaves `analysisPattern` unset and shows no such line. Pure frontend display; **no logic depends on it** (advisory still empty, diff base unaffected, Spec re-picks the real pattern at [spec.md:17](../../.claude/skills/dify-build/spec.md)).
3. **No test breakage — but two fixtures should be refreshed.** A1/A2/A3 touch no parser logic, so the suite stays green. **Correction (an earlier draft claimed "no test pins `find_query`" — that is wrong):** [analysis.test.ts:48-58](../../apps/builder/test/analysis.test.ts) *does* pin a `find_query` round-trip, and its fixture uses the very shorthand `find.py --has iteration` that A1 retires ([:52](../../apps/builder/test/analysis.test.ts)); [:68-73](../../apps/builder/test/analysis.test.ts) models the old minimal `{seed:null}` from-scratch shape A2 expands. Both still pass (synthetic inputs; parser unchanged), so **nothing breaks**. Only **one** fixture is worth refreshing for realism — the `find_query` round-trip at [:52](../../apps/builder/test/analysis.test.ts) → swap the shorthand for the canonical command string (cosmetic; the assertion value at [:57](../../apps/builder/test/analysis.test.ts) changes with it). **Do NOT mutate [:68-74](../../apps/builder/test/analysis.test.ts)** — that is the *back-compat* test (pattern-less `{seed:null}` → fields unset); changing its fixture would **delete real coverage** (exactly the impact to avoid). The new from-scratch shape (`pattern:"custom"` → no advisory) is **already** covered behaviorally by [:76-81](../../apps/builder/test/analysis.test.ts), so A2 needs no new test. A doc-drift test pinning "analyze.md uses the canonical command form" remains an optional *widening*, out of scope.

### The one open decision (recommended inline)

**Q — keep `find_query` or drop it, given nothing reads it?**
*Recommend **keep, scoped + corrected** (A1+A2).* It has live human-audit value on the **seed-present** path (where `find.py` genuinely classifies a real workflow), and 019 persisted it on purpose as the pattern-delta anchor that [diff.ts](../../apps/builder/server/lib/diff.ts) names as planned. The fix is a few doc edits (A1's two command sites + A2's from-scratch branch); dropping is the more *subtractive* move but undoes a deliberate forward-looking decision and costs a re-add later.
*Alternative — **fork F-A: drop `find_query` entirely** (remove from [analyze.md](../../.claude/skills/dify-build/analyze.md) schema + stop persisting in [analysis.ts](../../apps/builder/server/lib/analysis.ts) + drop `analysisFindQuery` from the task type).* Choose this **only if** the pattern-delta diff is formally cancelled (not deferred). Trigger: a decision that Phase-3+ pattern-delta will not ship. Until then, F-A trades a comment for churn.

## Considered & deliberately NOT done

- **F-A — drop `find_query` entirely.** More subtractive, but cancels 019's deferred-diff anchor. Deferred behind the explicit trigger above (pattern-delta formally cancelled).
- **F-B — make the advisory verify against `find_query` / build the pattern-delta diff.** The genuinely *additive* path. Owned by the [diff.ts](../../apps/builder/server/lib/diff.ts) Phase-3+ note, not this umbrella; this spec only guarantees that feature would inherit a *truthful* `find_query` instead of a fabricated one. Trigger: pattern-delta diff is scheduled.
- **A doc-drift test pinning "analyze.md uses the canonical `find.py` command".** Reasonable hardening, but no such drift test covers the skill `.md`s today; adding one is a separate widening, out of this XS scope.
- **P-1 — validate the `features` vocabulary at parse time.** *Pre-existing (019), surfaced by this spec's review but NOT introduced here.* Nothing enforces that `features[]` uses the find.py vocab ([analyze.md:30](../../.claude/skills/dify-build/analyze.md) only *asks* for it VERBATIM), so a typo (`web-search`, `LLM`) makes [`patternFeatureGap`](../../apps/builder/server/lib/analysis.ts) treat it as never-provided → a **phantom advisory** line ("missing feature(s) …"). It is advisory-only / non-blocking, so low severity, and validating it is a code change outside this doc-only umbrella. Trigger: the advisory graduates to anything that gates the build, OR a phantom advisory is observed in a real run.
